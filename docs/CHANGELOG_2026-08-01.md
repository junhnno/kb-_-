# 2026-08-01 수정 내역 — 오탐 감소 스위치 4종

## 요약

오탐(precision 30.9%, 깨끗한 상품당 평균 2.92개 허위 경고) 문제를 겨냥해 **스위치 4개**를 추가했음.
전부 **기본 꺼짐**이라 켜지 않으면 기존 동작과 완전히 동일함. 측정 후 켤지 말지 정하면 됨.

승우가 올린 오류 분석(pass12 실행)을 기준으로 만들었고, **보고된 오탐 패턴을 실제로 기각하는지까지 확인함.**

**중요: 네 스위치 모두 아직 실측 0건임.** 실제 정확도가 오르는지는 측정해봐야 앎.
테스트는 50개 → 63개로 늘었고 전부 통과함.

### 우선순위

`screen_situation`을 **가장 먼저** 재볼 것. 승우 분석에서 22건 중 7건으로 가장 큰 오탐 원인이었고,
보고된 오탐 문장 8건을 전부 기각하는 것까지 확인했음.

## 0. 근거 검증 레이어 — 라벨을 바꿀 수 있는 유일한 개입 (최우선)

### 실측이 말해준 것 (qwen3:14b, 22건, 시드 1회)

| | 단발 | 디베이트 |
|---|---|---|
| 적중률 8B | 77.3% | 47.6% |
| **적중률 14B** | **81.8%** (18/22) | **45.5%** (10/22) |
| gold=pass 정확도 8B | 8/12 | 0/12 |
| **gold=pass 정확도 14B** | **11/12** | **2/12** |

**모델을 8B → 14B로 키웠더니 단발은 거의 완벽해졌는데(pass 11/12) 디베이트는 그대로다.**
모델 능력의 문제가 아니라 구조의 문제다. 같은 모델·같은 케이스·같은 RAG인데,
심판 입력에서 다른 것은 **디베이트 전문뿐**이다. 회의론자 발언이 앞에 붙으면
같은 모델이 11/12에서 2/12로 떨어진다.

### 왜 프롬프트 수정으로 안 고쳐졌나

"경중을 따져라", "계산값과 모순되면 채택하지 말라"는 지시는 이미 두 번 넣었고 두 번 다 실패했다.
일반 규칙을 주면 **모델이 그 추론을 해내야 하는데, 그 추론이 바로 실패 지점**이기 때문이다.

### 한 일 — 추론을 시키지 않고 결과를 준다

회의론자 발화를 심판이 보기 **전에** 코드가 검증해서, "이 주장은 이래서 기각됨"을
항목별로 적어 심판 입력에 넣는다. 실제 주입 예시(CASE-014, gold=pass):

```
[코드 검증 결과 — 아래 주장은 주어진 사실과 직접 모순되어 기각되었다]
1. "중도해지 시 불이익에 대한 설명이 부족하다 [약관 제7조]"
   → 기각: 판매 정황에 '중도해지·중도상환 불이익' 설명 사실이 명시됨
2. "월 납입 부담이 과도하다"
   → 기각: 시스템 계산값과 모순 — 월 여유자금 240만원으로 감당 가능한 수준
3. "[preferential_unattainable] 우대조건 달성이 어렵다"
   → 기각: 시스템 계산값과 모순 — 이 상품에는 우대조건이 없음
4. "[dsr_overload] DSR 부담이 상당하다"
   → 기각: 시스템 계산값과 모순 — DSR 8.0% — 규제 한도(40%)에 미달

[지시] 위 기각 항목은 판정 근거로 삼지 말라. 남은 우려만으로 판정하라.
기각된 항목이 많다는 것은 제기된 우려에 비해 **실제 위험 근거가 약하다**는 뜻이다.
```

마지막 문장이 핵심이다. "우려가 제기되었다"는 압력을 "제기된 우려가 기각되었다"로 뒤집는다.

### 두 번째 개입 — 우려 목록과 라벨의 연결을 끊는다

검증 블록만으로는 부족하다. `JUDGE_SYSTEM`에 이런 규칙이 있다.

> **토론에서 제기된 우려는 누락 없이 옮긴다.** 계산값과 모순되거나 근거가 없어
> 기각하는 경우가 아니라면 목록에서 빼지 말라.

우려 발굴량을 살리려고 넣은 규칙인데(심판이 회의론자 우려 4종 중 3종을 버리던 문제),
부작용으로 **우려 목록이 채워지면 라벨이 따라서 warn으로 끌려간다.**
목록과 라벨이 붙어 있는 한 코드가 기각 목록을 넘겨줘도 효과가 상쇄된다.

그래서 둘을 명시적으로 끊었다. 목록은 그대로 다 채우고(recall 유지),
라벨은 네 조건을 **모두** 만족하는 우려에만 반응하게 했다.

```
[가장 중요 — 우려 목록과 적합성 라벨은 별개다]
우려 목록은 빠짐없이 채워라. 그것은 상품기획자가 검토할 항목이지 위반 판정이 아니다.
적합성 라벨은 아래 조건을 모두 만족하는 우려가 있을 때만 warn/fail로 준다.
  (1) 코드 검증에서 기각되지 않았다
  (2) 수치나 조항으로 뒷받침된다 (앵커가 있다)
  (3) 판매 정황상 이미 해소되지 않았다
  (4) 심각도가 '중대' 이상이다
위 네 조건을 다 만족하는 우려가 하나도 없으면 pass다. 우려를 5개 적었더라도 pass다.
우려의 개수는 라벨과 무관하다.
```

이 규칙은 `FDM_VERIFY_CLAIMS`와 **한 세트로만** 켜진다. 따로 켜면 baseline 비교가 깨진다.

### 세 번째 — 통과 건수를 알려준다

기각 목록만 보여주면 심판은 "그래도 나머지가 있으니 warn"으로 흐른다.
그래서 몇 건이 살아남았는지 함께 알린다. 전부 기각된 경우에는 이렇게 나간다.

```
[검증 요약] 회의론자 주장 3건 중 3건 기각, 0건 통과.
**검증을 통과한 위험 근거가 하나도 없다.** ... 이 경우 적합성은 pass다.
```

### 설계 원칙 — 탐지는 넓게, 판정은 검증된 근거로만

**회의론자 프롬프트는 손대지 않았다.** 우려 recall 96.7%는 이 시스템의 유일한 강점이라
그걸 깎으면 디베이트를 쓸 이유가 없어진다. 대신 역할을 나눈다.
회의론자는 민감도 높은 탐지기, 심판은 검증된 근거만 채택하는 필터.

### 왜 이것만 라벨을 바꿀 수 있나

기존 필터(1~3번)는 전부 **심판이 판정한 뒤에** 우려 목록만 손댄다. 라벨은 그대로다.
이 레이어만 심판의 **입력**을 바꾸므로 적중률·pass 정확도에 영향을 준다.

### 안전성 검증 — 이게 가장 중요하다

정당한 위반 지적을 기각하면 정답을 잃는다. 위반 케이스 10건 전부에 대해
실제로 제기될 법한 정당한 주장을 넣고 확인했다.

```
위반 케이스 10건(CASE-001~012 중 gold≠pass)의 정당한 주장 → 오기각 0건
깨끗한 케이스(CASE-014)의 허위 주장 4건                  → 4건 전부 기각
```

기각은 **검증 가능한 모순**에만 적용된다. 사실과 모순되지 않는 애매한 우려
("중도해지 이율이 다소 낮다")는 그대로 통과하며, 심판이 그걸로 warn을 줄 수 있다.
이 개입이 pass 2/12를 얼마나 올릴지는 열어놓고 봐야 한다.

## 1. 판매 정황 모순 스크리닝 (사후 필터)

### 문제

정답셋의 `facts`(판매 정황)는 **주어진 사실**인데 모델이 이걸 읽지 않고 정반대 주장을 함.
승우 분석에서 22건 중 최소 7건이 같은 패턴이었음.

```
CASE-014 정황 "중도해지 시 불이익을 설명했다"      → 출력 "중도해지 이자손실 설명이 부족"
CASE-008 정황 "중도해지 불이익을 표로 설명했다"     → 출력 "중도해지 불이익 설명 부족"
CASE-020 정황 "확정금리와 총 상환액을 안내했다"     → 출력 "금리 변동 가능성을 설명하지 않아"
```

이건 판단의 차이가 아니라 **입력과의 직접 모순**임. 기각 가능함.

### 왜 기존 스크리닝으로 안 잡혔나

`facts.CONTRADICTION_RULES`는 우려의 `type`으로 판정함. 그런데 CASE-020은 금리 변동을 문제 삼으면서
유형을 `explanation_insufficient`로 달았음. **유형이 어긋나면 규칙이 발동 안 함.**
그래서 새 모듈은 유형이 아니라 **문장 텍스트**로 봄.

### 작업 중 발견한 치명적 버그 (기록용)

초기 구현이 **부정문을 긍정으로 읽었음.**

```
CASE-004 "…시나리오는 안내받지 못했다"  → '안내함'으로 판정 (반대)
CASE-007 "…구조는 설명하지 않았다"      → '설명함'으로 판정 (반대)
CASE-010 "안내가 형식적으로만 이루어졌다" → '안내함'으로 판정 (부분이행인데)
```

이대로 넣었으면 gold=fail/warn 4건에서 **정답 우려를 지웠을 것.** 배선 전에 22건 전수 점검을 해서 잡았음.
부정 표현·부분이행 표현을 걸러내도록 고쳤고, 회귀 테스트로 고정함.

### 검증 결과

```
위반(fail/warn) 케이스 10건 → 오발동 0건
pass 케이스 12건          → 11건에서 정상 발동
보고된 오탐 문장 8건       → 8건 전부 기각
정당한 우려(부담률·이율 자체) → 유지 확인
```

### 안전장치

- 정황이 비어 있으면 아무것도 안 함
- 정황이 그 항목을 "설명했다"고 **명시**한 경우에만 발동 (언급 없으면 모름이지 아니오가 아님)
- "설명 부족" 주장에만 적용. 같은 항목의 다른 우려(예: "중도해지 이율이 낮다")는 안 건드림

## 1. 앵커 실재 검증 (신규 기능, 이번 작업의 핵심)

### 문제

`Concern.anchor`를 지금까지 **비어 있는지만** 검사했음(`schema.Concern.finalize`).
내용은 아무도 안 봤기 때문에, 모델이 존재하지 않는 `[약관 제10조]`를 지어내도 '치명' 심각도를 그대로 받았음.
산출물이 "여기를 보라"고 지목하는 도구인데 지목한 곳이 없으면 분석가 시간을 직접 낭비시킴.
(HANDOFF_PROMPT.md 6-5 항목에 미완료로 적혀 있던 것)

### 한 일

`src/fdm/anchors.py`를 새로 만들어, 앵커가 실제로 존재하는 것을 가리키는지 대조함.
검증 대상은 프롬프트가 허용한 인용 3종(`prompts.COMMON_RULES`)과 동일함.

| 종류 | 예시 | 대조 대상 |
|---|---|---|
| 약관·설명서 조항 | `[약관 제5조]` | 상품 JSON의 `clauses[].id` |
| 법령·문서 ID | `[FCPA-19]` | RAG 코퍼스의 `doc_id` |
| 재무 수치 | `[월 여유자금 106만원]` | 사실팩(FactPack) 계산값 |

실제 상품(SV-2026-001)으로 돌려본 판정 결과:

```
O 검증됨   '약관 제5조'          (실재)
X 지어냄   '약관 제10조'         (없는 조항)
O 검증됨   '[FCPA-19]'           (실재)
X 지어냄   '[FCPA-77]'           (없는 문서)
O 검증됨   '월 여유자금 106만원'  (사실팩과 일치)
- 검증불가 '중도해지 시 불이익 존재'
```

### 설계에서 신경 쓴 것

**3값 판정.** `검증불가`를 `지어냄`으로 취급하면 정당한 우려가 죽음.
자유 서술은 "틀렸다"가 아니라 "검증할 거리가 없다"로 따로 둠 (작업원칙 3번: 모름과 아니오를 구분).

**지우지 않고 강등.** 지어낸 인용은 심각도를 '경미'로 낮춰 T4(접어두기)로 보냄. 삭제 안 함 (작업원칙 4번).

**승격보다 먼저 검증.** 순서를 뒤집으면 `SEVERITY_FLOORS`가 올려놓은 심각도를 강등이 도로 깎음.
코드가 계산한 사실이 최종 판단이어야 하므로 `검증 → 승격` 순으로 배치함.

**병합 우선순위 반영.** `merge_concerns`(ensemble)에서 같은 유형이 겹칠 때
`검증된 앵커 > 앵커 있음 > 심각도` 순으로 남기게 바꿈.

### 승우 분석으로 잡은 결함 — 남의 조정례를 근거로 재활용 (4건)

```
CASE-013 앵커: [CASE-009]    CASE-015 앵커: [CASE-009]
CASE-017 앵커: [CASE-009]    CASE-018 앵커: [CASE-009]
```

RAG로 딸려온 남의 조정례를 자기 근거로 쓰고 있음. 자기 상품·페르소나·정황에서 인용한 게 아님.

**처음 만든 검증기는 이걸 못 잡았음.** CASE-009는 실존하는 문서라 doc_id 대조만으로는 통과함.
그래서 `borrowed` 상태를 따로 만들어, 조정례만 인용한 앵커는 심각도를 '주의'로 제한하게 고침.
프롬프트가 허용한 인용도 "법령·감독기준 문서"까지이지 조정례가 아님.
법령을 같이 인용했으면 정상 근거로 인정함.

## 2. 조정례 라벨 노출 차단

### 문제

`corpus.py`가 조정례 문서 제목을 이렇게 만들고 있었음.

```
조정사례(가공) 고령 예금 고객에게 원금손실 가능 파생결합증권 권유 — 판정 fail
```

코퍼스에 들어가는 조정례 12건 중 **10건(83.3%)이 fail/warn**임.
깨끗한 상품을 심사할 때도 "판정 fail"이 붙은 문서가 근거로 딸려오니 모델이 그 사전확률에 끌려감.

### 한 일

판단요지 본문은 그대로 두고 **제목의 라벨만 감추는** 옵션을 추가함.

조정례를 통째로 뺀 `single_lawonly` arm은 오히려 나빴음(적중률 77.3% → 59.1%).
즉 판단요지 본문 자체는 유용하고 라벨 노출만 해롭다는 뜻이므로, 그 중간을 따로 재보려는 것.

### 한계 (정직하게)

판단요지 본문에도 결론이 남아 있음. 예: "설명의무 위반을 인정했다", "개선을 권고했다".
12건 중 10건이 그런 식이라 **제목만 가려서는 사전확률 쏠림이 완전히 없어지지 않음.**
이 수정은 절반짜리이고, 얼마나 오르는지는 측정해봐야 앎.

---

## 3. 무근거 우려 제거

기존에는 앵커 없는 우려의 심각도를 '주의'로 캡만 씌웠는데, 채점은 유형 일치로 하므로 여전히 오탐으로 잡힘.
발굴량 자체를 줄이려면 제거가 필요해서, 앵커 없는 우려를 아예 목록에서 빼는 옵션을 추가함.

기존 캡 방식보다 공격적이라 **recall을 깎을 위험이 큼.** precision만 보지 말고 recall도 같이 찍어야 함.

## 실행 방법

```bash
python scripts/run_ab_experiment.py --seeds 1 --arms single --only baseline,screen_situation
```

`--only` 뒤를 갈아끼우면 조건이 바뀜:
`baseline`, `screen_situation`, `hide_label`, `verify_anchors`, `drop_unanchored`, `all`.

실행기가 하는 일:

- 조건마다 **별도 프로세스**로 실행함. 설정과 코퍼스가 모듈 로드 시점에 캐시돼서, 한 프로세스에서 환경변수만 바꾸면 반영이 안 됨
- 결과를 `outputs/ab_<조건명>.json`으로 따로 저장함 (기존 `fdm ablation`은 항상 `ablation.json` 하나에 덮어씀)
- 20초마다 로그를 흘려 보여줌. 1시간 블랙박스로 기다리다 중간에 죽이는 일 방지

## 측정할 때 주의할 것

**한 번에 하나씩 켤 것.** `all`도 넣어뒀지만 개별 효과를 확인한 뒤에만 의미가 있음.
동시에 켜면 어느 게 기여했는지 나눌 수 없음.

**앵커 검증은 라벨 지표에서 효과가 0으로 보임.** 우려의 *심각도*만 바꾸고 라벨은 안 건드리기 때문임.
그대로 뒀으면 실험 돌리고 "효과 없네"라는 잘못된 결론을 낼 뻔했음.
그래서 실행기에 **우려 단위 지표표**(recall / precision / 과잉경고 / 앵커 검증률)를 따로 추가했고,
채점 로직은 `analyze_ablation.py`에서 그대로 가져와 재사용함(같은 계산을 두 벌 두면 반드시 어긋남).

**모델은 `qwen3:8b`로 고정할 것.** 기존 측정치(적중률 77.3%, precision 30.9%)가 전부 8b 기준이라
14b로 바꾸면 비교가 성립하지 않음.

**노이즈 주의.** 정답셋 22건(pass 12 / warn 5 / fail 5)이라 1건 = 4.5%p임.
웬만한 차이는 노이즈와 구분되지 않음.

**변형을 계속 늘리는 것 자체가 위험함.** 같은 22건에 여러 설정을 시험하면
그중 하나는 순전히 운으로 좋아 보임. 새 아이디어보다 이미 만든 3개를 재는 게 우선임.
